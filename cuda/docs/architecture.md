# Архитектура VecLens

VecLens — движок приближённого поиска ближайших соседей на GPU, построенный
по схеме IVF-Flat: база разбивается на `nlist` инвертированных списков вокруг
обученных центроидов, запрос сравнивается сначала с центроидами, затем — с
векторами `nprobe` ближайших списков.

## Слои

```
                       apps/veclens_cli.cpp        C-API (veclens_c.h)
                                │                          │
    ┌───────────────────────────┴──────────────────────────┴──────────────┐
    │  Прикладной слой                                                    │
    │  QueryPipeline · StreamingIvfIndex · ShardedIvfIndex · AutoTuner    │
    └───────────────────────────┬─────────────────────────────────────────┘
                                │
    ┌───────────────────────────┴─────────────────────────────────────────┐
    │  Слой индекса                                                       │
    │  IvfFlatIndex · FlatIndex · KMeans · IndexSerializer                │
    └───────────────────────────┬─────────────────────────────────────────┘
                                │
    ┌───────────────────────────┴─────────────────────────────────────────┐
    │  Слой ядер                                                          │
    │  distance · topk · scan · warp_primitives · block_reduce            │
    └───────────────────────────┬─────────────────────────────────────────┘
                                │
    ┌───────────────────────────┴─────────────────────────────────────────┐
    │  Слой рантайма                                                      │
    │  common (проверки) · DeviceBuffer/PinnedBuffer · Stream/Event ·     │
    │  MemoryPool/ScratchArena · NVTX · GpuMonitor · JitKernelCache       │
    └─────────────────────────────────────────────────────────────────────┘
```

Правило слоёв: вызовы идут только вниз. Ядро не знает об индексе, индекс не
знает о конвейере. Единственное исключение — `common.hpp`, который доступен
отовсюду: без проверки кода возврата CUDA не обходится ни одна строка.

## Зависимости модулей

```
  types.hpp ◄──────────────────────────────── все остальные заголовки
     ▲
  common.hpp ◄── device_buffer.hpp ◄── allocator.hpp
     ▲                 ▲
  stream.hpp ──────────┤
                       │
  warp_primitives.cuh ─┼──► block_reduce.cuh ──► distance.cuh ──┐
                       │                                        │
                       └──► scan.cuh ──────────────────────────►│
                                                                ▼
  dataset.hpp ──► kmeans.hpp ──► ivf_index.hpp ◄── topk.hpp ────┘
                                      ▲
        ┌─────────────────┬───────────┼────────────┬────────────────┐
        │                 │           │            │                │
  pipeline.hpp   streaming_index.hpp  │      multi_gpu.hpp    autotune.hpp
                                index_io.hpp

  jit_kernel.hpp, monitor.hpp — самостоятельные, зависят только от types.hpp
  cpu_reference.hpp — зависит от dataset.hpp, не зависит от CUDA-кода
```

`jit_kernel.hpp` и `monitor.hpp` намеренно не связаны с индексом: JIT
компилирует ядро по ключу, монитор читает NVML. Их можно выкинуть из сборки,
и движок продолжит работать.

## Владение памятью

| Ресурс | Владелец | Время жизни |
|---|---|---|
| Векторы базы на устройстве (`list_data_`) | `IvfFlatIndex` | от `build()` до разрушения индекса |
| Центроиды, смещения списков, нормы | `IvfFlatIndex` | то же |
| Временные буферы одного запроса | `ScratchArena` внутри индекса | переиспользуются между запросами |
| Буферы слота конвейера | `QueryPipeline::Slot` | всё время жизни конвейера |
| Закреплённые буферы ввода-вывода | `PinnedBuffer` в слоте | то же |
| Индекс в потоковом режиме | `StreamingIvfIndex::Impl` (pinned или managed) | всё время жизни объекта |
| Резидентная часть (HotCold) | `DeviceBuffer` в `Impl` | то же |
| Память шарда | `ShardedIvfIndex::Impl::Shard` | освобождается в контексте своей карты |
| Выходные массивы C-API | вызывающая сторона | движок только заполняет |
| Модули NVRTC | `JitKernelCache::Impl` | до разрушения кэша |

Три правила, из которых всё это следует:

1. Владение всегда однозначно. Ни один буфер не имеет двух владельцев,
   поэтому копирующие конструкторы `DeviceBuffer` и `PinnedBuffer` удалены —
   неявная копия гигабайта не должна получаться из знака `=`.
2. Память устройства освобождается в контексте своей карты. В multi-GPU это
   явный `cudaSetDevice` в деструкторе шарда.
3. В горячем пути нет `cudaMalloc`. Он синхронизирует устройство, поэтому
   всё, что нужно запросу, выделено заранее: арена, слоты конвейера,
   буферы чанков.

## Поток данных одного запроса

```
  хост                            │  устройство
  ────────────────────────────────┼──────────────────────────────────────────
  1. батч запросов                │
     упаковка в pinned-буфер      │
     (дополнение до dim_padded)   │
                                  │
  2. cudaMemcpyAsync H2D ────────►│  d_queries [nq x dim_padded]
                                  │
                                  │  3. coarse: запрос x центроиды
                                  │     launch_coarse_distances
                                  │     ──► d_coarse [nq x nlist]
                                  │
                                  │  4. отбор nprobe списков
                                  │     launch_topk
                                  │     ──► d_probe_lists [nq x nprobe]
                                  │
                                  │  5. обход списков
                                  │     ядро scan по CSR-раскладке
                                  │     ──► d_candidates [nq x candidates]
                                  │
                                  │  6. top-k по кандидатам
                                  │     launch_topk / launch_merge_topk
                                  │     ──► d_out [nq x k]
                                  │
  7. cudaMemcpyAsync D2H ◄────────│
     событие слота                │
  8. SearchResult                 │
```

Стадии 3–6 в конвейере захвачены в CUDA Graph: их форма не меняется от батча
к батчу, а запуск графа стоит одного вызова драйвера вместо десятка.

Кольцевой буфер конвейера удерживает `depth` батчей одновременно: пока
батч `i` считается, батч `i+1` уже едет по PCIe. Перед перезаписью
pinned-буфера слот ждёт своё событие — иначе копирование, которое ещё не
завершилось, увидит чужие данные.

## Три режима работы с памятью

| Режим | Когда | Цена |
|---|---|---|
| Всё в VRAM (`IvfFlatIndex`) | база помещается на карту | ничего лишнего |
| `StreamingIvfIndex::Chunked` | база больше VRAM | трафик PCIe на каждый запрос, скрыт двойной буферизацией |
| `StreamingIvfIndex::Unified` | база больше VRAM, доступ разреженный | миграция страниц драйвером, `ReadMostly` + `prefetch` |
| `StreamingIvfIndex::HotCold` | распределение списков смещённое | горячая часть резидентна, холодная приходит потоком |
| `ShardedIvfIndex` | есть несколько карт | сбор частичных top-k, NCCL или через хост |
