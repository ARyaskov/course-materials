# Тестирование

## Каркас

Тесты используют собственный header-only harness `tests/test_main.hpp`:
макросы `VL_TEST(имя)`, `VL_CHECK(условие)`, `VL_CHECK_NEAR(a, b, eps)`,
регистрация статическим объектом, `main` в самом заголовке под
`VL_TEST_MAIN`. Каждый тестовый файл определяет `VL_TEST_MAIN` перед
подключением заголовка.

Внешнего фреймворка нет намеренно: на десяток файлов он добавил бы больше
времени сборки, чем экономит кода, а в CI-контейнере — ещё и зависимость.

```cpp
#define VL_TEST_MAIN
#include "test_main.hpp"

VL_TEST(имя_теста) {
  VL_CHECK(2 + 2 == 4);
  VL_CHECK_NEAR(0.1 + 0.2, 0.3, 1e-9);
}
```

## Запуск

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=RelWithDebInfo -DVECLENS_BUILD_TESTS=ON
cmake --build build -j
ctest --test-dir build --output-on-failure

./build/test_topk                # весь файл
./build/test_topk topk_single    # только тесты, чьё имя содержит подстроку
```

Фильтр по подстроке нужен прежде всего для санитайзеров: под
`compute-sanitizer` полный набор идёт минутами.

## Что покрыто

| Файл | Что проверяет |
|---|---|
| `test_buffers.cu` | `DeviceBuffer` / `PinnedBuffer`: round-trip копирований, `zero`, move-конструктор и move-присваивание (источник остаётся пустым и валидным), безопасность самоприсваивания, `resize` (тот же размер не перевыделяет, ноль освобождает), отсутствие утечек по `cudaMemGetInfo` после 32 циклов выделения |
| `test_warp_primitives.cu` | `warp_reduce(SumOp)`, `warp_all_reduce(MaxOp)` (результат одинаков во всех полосах), `warp_inclusive_scan`, `warp_reduce_argmin` (при равных значениях побеждает меньший индекс), `warp_aggregated_atomic_inc` (слоты образуют перестановку, счётчик равен числу потоков) — всё против CPU-эталона |
| `test_scan.cu` | `launch_exclusive_scan` против `std::exclusive_scan` на размерах 1, 32, 1023, 1024, 2^20; ненулевой размер scratch-буфера; `launch_histogram` против подсчёта на хосте на смещённом распределении и на одном бине |
| `test_topk.cu` | все три алгоритма против `std::partial_sort` для L2 и inner product; вырожденные случаи: все значения равны, `k == cols`, одна строка, `k = 1`; границы `select_topk_algo`; `launch_merge_topk` против прямого top-k |
| `test_kmeans.cu` | сходимость к известным центрам на синтетических кластерах (взаимно однозначное соответствие центроидов и истинных центров), невозрастание инерции по итерациям, отсутствие пустых кластеров, совпадение разбиения с истинным с точностью до перенумерации |
| `test_ivf.cu` | сумма длин списков равна `n`; согласованность CSR-смещений с длинами; каждый вектор ровно в одном списке (идентификаторы — перестановка `0..n-1`); `recall@10 ≥ 0.99` при `nprobe == nlist`; осмысленный recall при малом `nprobe` |
| `test_index_io.cu` | round-trip `save`/`load`: совпадение длин списков и результатов поиска до идентификаторов; выравнивание секций на 256 байт и монотонность смещений; размер файла равен `total_bytes`; отказ на чужом файле, отсутствующем файле и файле неподдерживаемой версии |

Про `recall@10` при `nprobe == nlist`: при просмотре всех списков кандидаты
те же, что у полного перебора, поэтому recall равен единице. Тест требует
`>= 0.99`, потому что при совпадающих расстояниях порядок соседей на границе
top-k — законная перестановка, и требовать конкретную было бы проверкой не
свойства алгоритма, а деталей реализации сортировки.

## Чего тесты не проверяют

* `QueryPipeline`, `StreamingIvfIndex`, `ShardedIvfIndex` — их поведение
  зависит от объёма памяти и числа карт, поэтому они проверяются
  бенчмарками и демонстрационным прогоном, а не ctest.
* JIT-путь (`JitKernelCache`) — компиляция требует NVRTC в окружении;
  `generate_scan_kernel_source` при этом работает всегда и пригодна для
  сравнения с эталонным текстом.
* NVML-мониторинг — недоступен в контейнере без проброшенных устройств.

## Санитайзеры

```bash
./scripts/sanitize.sh                                   # все режимы, все тесты
TOOLS=racecheck TESTS=test_topk ./scripts/sanitize.sh   # точечно
```

| Режим | Что ищет | Типичная находка в таком проекте |
|---|---|---|
| `memcheck` | выход за границы буферов, некорректные обращения, утечки памяти устройства | индексация `row * cols + i` без проверки хвоста; забытый `release()` |
| `racecheck` | гонки в shared memory | пропущенный `__syncthreads()` между записью и чтением общего массива, например в битонической сортировке |
| `initcheck` | чтение неинициализированной глобальной памяти | буфер результата, в который записали не все строки |
| `synccheck` | некорректные барьеры и warp-примитивы | `__syncthreads()` в расходящейся ветке; `__shfl_*_sync` с маской, не совпадающей с набором активных полос |

Санитайзер замедляет выполнение в десятки раз. `memcheck` запускается с
`--leak-check full`, остальные режимы этот флаг не поддерживают. Ненулевой
код возврата обеспечивается `--error-exitcode 1`, логи складываются в
`build/sanitizer-logs`.

Отдельно: сборка проекта идёт с `-Xptxas=-v`, поэтому в логе сборки видны
регистры и shared memory каждого ядра. Рост регистров на ядро — первый
признак того, что занятость упала, и его лучше замечать при сборке, а не в
профилировщике.

## CI

`scripts/ci.sh` выполняет полный цикл: сборка → `ctest` → санитайзеры →
бенчмарки → сравнение с базовой линией (`bench/baseline.json`, порог
замедления 10%). Шаги отключаются переменными `SKIP_SANITIZERS=1` и
`SKIP_BENCH=1`.
