# Руководства по инцидентам Pulse

Каждое руководство: признаки → диагностика → действия по порядку → критерий завершения → исправление в источнике.
Запросы — `queries/ch18_incidents.sql`, `queries/ch18_mutations.sql`, `queries/ch12_diagnostics.sql`.

## 1. Too many parts (код 252)

**Признаки.** Вставки отказывают с `Too many parts`; до этого — `DelayedInserts` > 0, `MaxPartCountForPartition` > 300, загрузка «стала медленной».

**Диагностика.**
1. Куски по партициям: `system.parts` (active) — где именно.
2. Кто создаёт: `system.query_log` за 30 минут по `user`, `client_name`, среднему `written_rows` вставки.
3. Средний размер куска в сообщении: килобайты = мелкие вставки; мегабайты = слияния не успевают (`system.merges`, пул).

**Действия.**
1. Остановить источник мелких вставок (или временно включить `async_insert` в его профиле).
2. Убедиться, что слияния идут: `SYSTEM START MERGES pulse.events`; при пустой очереди и множестве кусков — `OPTIMIZE TABLE pulse.events PARTITION '<p>'`.
3. Только если приток остановить нельзя — временно поднять `parts_to_throw_insert`/`parts_to_delay_insert` с записанным планом возврата.

**Завершение.** Кусков в партиции < 100, `DelayedInserts` не растёт, пороги возвращены.

**Исправление в источнике.** Батчинг (10 000 строк / 1–2 с), `async_insert` в профиле загрузчика, крупные блоки потребителя Kafka, backfill по партициям, партиции не мельче срока хранения, оповещение по `MaxPartCountForPartition > 300`.

## 2. Memory limit exceeded (код 241)

**Признаки.** Ошибка с уровнем: `for query` / `for user` / `total`.

**Диагностика.**
1. Уровень — из текста. `total`: `system.processes` по памяти + ревизия `system.dictionaries` (bytes_allocated), кэшей, слияний.
2. Запрос: `EXPLAIN` — `Aggregating` по высокой кардинальности, `Join` с большой правой стороной, `Sorting` без `Limit`, окно без партиции.
3. Пик — `memory_usage` в `system.query_log`.

**Действия.**
1. `total`: `KILL QUERY` самого прожорливого; проверить словари/кэши; при необходимости временно снизить их.
2. Запрос: дешёвое (приближённые функции, `groupArray(N)`, `LIMIT`, узкий период) → среднее (`max_bytes_before_external_group_by/sort`) → архитектурное (витрина, проекция, словарь, `grace_hash`).
3. Пользователь: `max_memory_usage_for_user`, квота, класс нагрузки.

**Завершение.** Запрос выполняется в лимите; остальные не затронуты.

**Не делать.** Поднимать `max_memory_usage` профиля «чтобы прошло» — лимит защищает остальных.

## 3. Застрявшая мутация

**Признаки.** `system.mutations`: `is_done = 0`, `parts_to_do` не убывает, `latest_fail_reason` не пуст; последующие мутации ждут.

**Диагностика.** Причина в `latest_fail_reason`: нет места на диске, выражение падает на строке (переполнение, деление на ноль, приведение), колонка удалена, повреждённый кусок.

**Действия.**
1. Устранить причину (место, выражение с `OrZero`/`OrNull`).
2. `KILL MUTATION WHERE database = 'pulse' AND table = '<t>' AND mutation_id = '<id>'`.
3. Повторить исправленную мутацию с `mutations_sync = 1` или восстановить период через staging + `REPLACE PARTITION` (частично применённая мутация оставляет часть кусков обновлёнными).

**Завершение.** `system.mutations` без незавершённых; данные периода сверены.

**Исправление в источнике.** Мутации — только с оценкой объёма (`system.parts` по затронутым партициям), в окно низкой нагрузки, по одной; для типовых задач — партиции, `ReplacingMergeTree`, облегчённое удаление.

## 4. Восстановление после ошибочной команды / потери таблицы

**Действия.**
1. Остановить загрузку в затронутую таблицу.
2. `RESTORE TABLE pulse.<t> AS pulse_restore.<t> FROM S3(minio_backups, filename = '<последняя копия>/')`.
3. Сравнить счётчики за закрытый период; вернуть на место: `RESTORE TABLE pulse.<t> FROM ...` (или `ATTACH PARTITION FROM pulse_restore.<t>` для недостающих партиций).
4. Дозагрузить период между копией и ошибкой из брокера/сырого слоя/озера; сверить.
5. Проверить, что материализованные представления снова пишут (минута загрузки + сверка последнего часа).
6. Возобновить загрузку.

**Цели.** Потеря данных не более суток (ежедневная инкрементальная копия); восстановление таблицы — минуты, базы — по объёму. Репетиция — `scripts/restore_drill.sh` ежемесячно; время записывать ниже.
