# Архитектура Pulse: паттерны и решения

Документ фиксирует, какие архитектурные паттерны реализованы в проекте, какие решения приняты в каждом и где они могут быть приняты иначе (глава 19).

## Схема

```text
 источники            доставка            хранилище                  потребители
 ┌──────────┐   ┌──────────────┐   ┌─────────────────────────┐   ┌──────────────┐
 │ backend  │──▶│ буфер/Kafka  │──▶│ raw ─▶ events ─▶ витрины│──▶│ дашборд      │
 │ клиенты  │──▶│ коллектор    │   │   │        │       │     │──▶│ поддержка    │
 │ PG (CDC) │──▶│              │   │ логи  метрики  трассы   │──▶│ аналитики    │
 └──────────┘   └──────────────┘   │ архив (озеро), холодный │──▶│ продукт (API)│
                                   └─────────────────────────┘   └──────────────┘
```

## Паттерн 1. PostgreSQL + ClickHouse

- **Роли:** PostgreSQL — источник истины для сущностей; ClickHouse — события, история версий, агрегаты.
- **Пути данных:** события из приложения (Pulse); справочники — словари с источником PostgreSQL; изменяемые сущности — поток изменений в `ReplacingMergeTree(version, is_deleted)` (`ddl/orders_cdc.sql`).
- **Не делаем:** чтение живого PostgreSQL из каждого отчёта; экспериментальный движок репликации базы в продакшене.
- **Иначе можно:** периодическая выгрузка по метке времени — для источников без логической репликации.

## Паттерн 2. Конвейер событийной аналитики

- **Схема события:** ядро (время, пользователь, сессия, тип, endpoint, статус) + `attributes Map`; частые атрибуты выносятся в колонки (`plan`, `endpoint_group`).
- **Идентификаторы и время:** `session_id` UUID, `event_time` (источник) и `received_at` (приём); партиции и витрины — по времени события, границы backfill — по времени приёма.
- **Доставка:** буфер в приложении (2 порога, токен идемпотентности, сброс на диск) → `events_in`; внешние источники → Kafka → `raw_events` → разбор представлением.
- **Дедупликация:** блочная на вставке + токен; логическая — на чтении при необходимости; сверки витрин.
- **Слои и сроки:** сырьё 3 дня; события 30 дней горячие + до 90 холодные; витрины 2 года; озеро бессрочно.
- **Качество:** доля без пользователя, расхождение часов, объём по источникам, сверка витрин — `queries/ch19_dashboard_api.sql` и `ch10_dashboard.sql`.

## Паттерн 3. Хранилище телеметрии

- Точка входа `logs_in` с маршрутизацией (ошибки — долго, DEBUG — выборка 10 % и 2 дня), метрики узкой схемой + минутная витрина, спаны с индексами по идентификаторам, общие `request_id`/`trace_id`.
- Ориентиры полного размера: логи сжимаются ×10–20, метрики ×100+; уровни хранения; метки с высокой кардинальностью — в логи и трассы, не в метрики; оповещения по метрикам — у сборщика, по логам и истории — в ClickHouse; самонаблюдение — вне хранилища.

## Паттерн 4. Лёгкое хранилище данных

- Слои: сырой (`raw_events`, `orders_cdc_in`), чистый (`events`, `orders`, `user_profiles`, история тарифов), витрины (`*_hourly*`, `retention_*`, снимки).
- Моделирование: широкая таблица фактов + словари; история измерений — версии с интервалами; суррогатные ключи — хеши; метрики — представления (`v_hourly_activity`).
- Преобразования как код: DDL в репозитории; при росте — инструмент моделей поверх SQL с адаптером ClickHouse.
- Граница «лёгкого»: сложные соединения многих больших таблиц, транзакционные обновления, произвольный SQL без дисциплины, строгая изоляция вычислений.

## Паттерн 5. Живой дашборд

- Витрина по минутам + хвост по событиям за 2–3 минуты в одном запросе; кэш результатов 10 с; параметризованные запросы с меткой панели; «по состоянию на» — общий параметр экрана.
- Путь: клиент → сервис приложения → ClickHouse (пользователь `dashboard`, профиль, квота, политики строк). Клиент никогда не ходит в базу напрямую.

## Антипаттерны, которых в проекте нет

OLTP-использование, построчные вставки, таблица на арендатора, мелкие партиции, `FINAL` везде, ночной `OPTIMIZE FINAL`, `SELECT *` без периода, соединения больших таблиц, мутации как повседневность, таблицы без TTL, один пользователь на всех, устаревшие рецепты (Live View, Ordinary, ZooKeeper-only), экспериментальное без проверки, скопированные настройки, отсутствие мониторинга.
