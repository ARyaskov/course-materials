# Принятые решения по Tessera

Короткие записи «что решили и почему». Каждая запись избавляет от повторного спора
через полгода, когда контекст забыт.

## Redis критичен для readiness

`/readyz` возвращает 503 при недоступном Redis, то есть под целиком выводится из балансировки.
Альтернатива — считать Redis некритичным и отвечать 503 только на эндпоинтах брони.
Выбран строгий вариант: билеты продаются по конкретным местам, и без брони работа сервиса
теряет смысл, а частичная доступность запутывает покупателя.

## Один ConfigMap на сервис

`api` и `worker` читают почти одинаковый набор переменных, поэтому конфигурация лежит
в одном объекте. Цена — перекат обоих workload'ов при любой правке; для сервиса такого
размера это приемлемо.

## Цельный DSN вместо частей

Строка подключения к PostgreSQL хранится целиком в Secret, а не разбирается на хост,
порт, пользователя и пароль. Библиотека принимает именно DSN; сборка строки из частей
добавила бы код без практической пользы.

## Ключ подписи билетов — в переменной окружения

`TESSERA_TICKET_SIGN_KEY` читается при старте вместе с остальной конфигурацией.
После смены внешнего Secret нужен rolling restart; горячего перечитывания нет.
Учебный сервис проверяет подпись одним ключом. Ограничения ротации и судьба
старых билетов описаны в `secrets.md`.

## Перезапуск при смене конфигурации — через аннотацию с хэшем

Выбран `checksum/config` в аннотации шаблона пода, а не иммутабельные ConfigMap
с хэшем в имени. Сервис небольшой, накопление объектов конфигурации в неймспейсе
мешает больше, чем даёт атомарность отката.

## Автомасштабирование по CPU, не по метрикам приложения

`autoscaling.extraMetrics` предусмотрен, но по умолчанию пуст: адаптер метрик
есть не в каждом кластере, а чарт не должен требовать компонента, которого
может не быть. Метрика очереди броней добавляется в production-профиле там,
где адаптер установлен.

## PodDisruptionBudget через maxUnavailable

При включённом автомасштабировании `minAvailable` с абсолютным значением
блокирует обслуживание узлов при сокращении до минимума. `maxUnavailable: 25%`
масштабируется вместе с числом реплик.

## Чарт не создаёт объектов уровня кластера

Ни `ClusterRole`, ни `PriorityClass`, ни `StorageClass`. Они глобальны,
и два релиза в разных неймспейсах за них конкурируют. Чарт только ссылается
на имена, созданные платформой.

## Umbrella только для стендов и превью

`charts/tessera-env/` используется в dev и превью-окружениях, где всё
создаётся и удаляется вместе. В staging и production ставится чарт сервиса
напрямую: база и кэш живут снаружи и имеют собственный цикл релиза.
