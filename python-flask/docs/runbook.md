# Эксплуатация

Что делать, когда что-то идёт не так. Документ пишется до инцидента:
во время инцидента его читают, а не сочиняют.

## Признаки здоровья

| Сигнал | Где смотреть | Норма |
| --- | --- | --- |
| Процесс жив | `GET /healthz` | 200 всегда, пока процесс отвечает |
| Готов к трафику | `GET /readyz` | 200; 503 при недоступной базе или во время остановки |
| Версия | `GET /version` | совпадает с выложенной |
| Доля 5xx | журнал, поле `status` | ниже 0,5% за пять минут |
| Задержка | журнал, поле `duration_ms` | 95-й процентиль ниже 300 мс |
| Длина очереди | `rq info` | не растёт монотонно |

Проверка живости не трогает базу намеренно: иначе недоступность базы
перезапустит все реплики разом и добавит к отказу базы отказ приложения.

## Диагностика по идентификатору запроса

В каждом ответе есть заголовок `X-Request-Id`; он же — в теле ошибки
и в каждой строке журнала запроса. По жалобе пользователя достаточно
попросить этот идентификатор.

```bash
docker compose logs api | grep '"request_id":"<id>"'
```

Фоновые задачи получают идентификатор вызвавшего запроса в полезной
нагрузке, поэтому цепочка прослеживается через очередь.

## Частые ситуации

### Растёт доля 503

Смотреть код ошибки в теле: `database_unavailable`, `cache_unavailable`,
`queue_unavailable` и `dependency_unavailable` означают разные причины.

`dependency_unavailable` — сработал предохранитель на платёжном шлюзе.
Это не сбой Depot: предохранитель перестал звонить в сервис, который
не отвечает. Восстановление автоматическое, через полуоткрытое
состояние.

### Очередь растёт

```bash
rq info --url "$DEPOT_REDIS_URL"
```

Сначала проверить, живы ли воркеры и не падают ли задачи по одной и той
же причине (`failed` в `rq info`). Добавление воркеров при систематически
падающей задаче лишь ускоряет накопление ошибок.

### Брони «зависли» в состоянии ожидания

Периодическая задача `expire_stale_holds` идёт раз в минуту. Если она
не выполняется, удержания снимаются вручную:

```bash
flask --app depot:create_app expire-holds --limit 500
```

Команда идемпотентна: подтверждённые и отменённые брони она не трогает.

### Двойное начисление штрафа

Невозможно: уникальное ограничение `uq_invoice_lines_kind_day` не
допускает две строки одного вида за одни сутки по одному счёту. Если
жалоба поступила, искать нужно две разные аренды по одной броне —
такого тоже не бывает, `uq_rentals_booking` это запрещает.

## Выкладка

1. `flask db upgrade` отдельной задачей до переключения трафика.
   Миграция берёт консультативную блокировку, поэтому одновременный
   запуск на нескольких экземплярах безопасен.
2. Экземпляры обновляются по одному, режим `start-first`.
3. При получении SIGTERM приложение перестаёт проходить проверку
   готовности и дорабатывает текущие запросы. Период ожидания
   оркестратора должен быть больше `graceful_timeout` в настройках
   сервера приложений.

Миграции пишутся совместимыми в обе стороны: сначала выкладывается схема,
принимающая старый и новый код, затем код, затем удаляется лишнее. Иначе
откат версии приложения невозможен без отката базы.

## Ротация ключа подписи

1. Записать действующий ключ в `DEPOT_SECRET_KEY_PREVIOUS`, идентификатор —
   в `DEPOT_TOKEN_KEY_ID_PREVIOUS`.
2. Новый ключ — в `DEPOT_SECRET_KEY`, новый идентификатор — в
   `DEPOT_TOKEN_KEY_ID`.
3. Выложить. Новые токены подписываются новым ключом, старые ещё
   принимаются.
4. Через время жизни токена доступа убрать прошлый ключ.

Пропуск шага с прошлым ключом мгновенно разлогинивает всех, у кого токен
доступа ещё жив.

## Резервное копирование

Проверяется не наличие копии, а возможность восстановления:

```bash
./deploy/backup.sh
```

Скрипт снимает копию и разворачивает её во временную базу, проверяя, что
число строк в основных таблицах совпадает. Копия, которую ни разу не
разворачивали, — это предположение, а не резервная копия.
