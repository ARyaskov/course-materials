# Принятые решения

Короткие записи о выборах, которые неочевидны при чтении кода. У каждой —
контекст, решение и цена. Записи не переписываются: если решение изменилось,
добавляется новая со ссылкой на прежнюю.

## 1. Пересечение броней проверяет база, а не приложение

**Контекст.** Одна единица оборудования не может быть занята двумя
арендаторами одновременно. Очевидная реализация — запрос «есть ли
пересекающаяся бронь» перед вставкой.

**Проблема.** На уровне изоляции READ COMMITTED два параллельных запроса
оба видят свободный интервал: конфликтующей строки в момент проверки ещё
нет ни в одной из транзакций. Обе вставки проходят.

**Решение.** Ограничение исключения PostgreSQL с индексом GiST по
`unit_id` и диапазону времени, включающему буфер на осмотр. Приложение
по-прежнему делает предварительную проверку — ради понятного сообщения,
но гарантию даёт база.

**Цена.** Требуется расширение `btree_gist`; логика оказывается частично
в миграции, и её нужно держать согласованной с `domain/rules.py`. Значение
буфера продублировано в миграции намеренно: миграция должна оставаться
воспроизводимой при изменении кода.

## 2. Токен доступа не проверяется по базе

**Контекст.** Проверка токена происходит на каждом запросе.

**Решение.** Подписанный JWT с коротким сроком жизни (15 минут), проверка
без обращения к хранилищу. Токен обновления, напротив, хранится в базе
в виде хеша и отзывается мгновенно.

**Цена.** Отзыв прав вступает в силу с задержкой до срока жизни токена.
Для немедленного отзыва есть массовый механизм: момент смены пароля
в теле токена сверяется с записью пользователя.

## 3. Чужой объект даёт 404, а не 403

**Контекст.** Клиент запрашивает бронь другого пользователя.

**Решение.** `NotFound`. Ответ 403 подтвердил бы, что объект с таким
идентификатором существует, — это ответ на вопрос, которого не задавали.

**Цена.** Отладка становится менее удобной: разработчик не отличает
опечатку в идентификаторе от нехватки прав. Разница видна в журнале,
где сохраняется настоящая причина.

## 4. Список ролей не наследуется

**Контекст.** Три роли: клиент, оператор, администратор.

**Решение.** Набор прав каждой роли перечислен полностью, без
наследования от «младшей». Код проверяет право, а не роль.

**Цена.** Таблица длиннее. Взамен добавление права не расширяет молча
полномочия ролей, о которых при этом не думали.

## 5. Постановка задач — после фиксации транзакции

**Контекст.** Подтверждение брони должно отправить письмо.

**Решение.** Задача ставится в очередь после `commit`. Внутри транзакции
это привело бы к письму об операции, которая откатилась.

**Цена.** Открывается окно: транзакция зафиксирована, процесс упал до
постановки. Окно закрывает периодическая задача, восстанавливающая
состояние из данных, — по флагу `notification_pending` и по сроку
удержания.

## 6. Деньги — только `Decimal`

**Контекст.** Ставки, залоги, штрафы, суммы счетов.

**Решение.** `Numeric(12, 2)` в базе, `Decimal` в коде, строка в JSON.
Округление — явное, `ROUND_HALF_UP`.

**Цена.** Дополнительное преобразование на границах и невозможность
использовать арифметику с плавающей точкой в расчётах. Встроенное
округление в Python банковское (к чётному), поэтому оно задаётся явно:
для денег ожидается школьное.

## 7. Разные схемы для входа и выхода

**Контекст.** Соблазн описать сущность одной схемой.

**Решение.** `InputSchema` с `extra="forbid"` и `OutputSchema`
с `from_attributes=True` — разные базовые классы.

**Цена.** Больше кода. Взамен поле, добавленное в ответ, не начинает
приниматься в запросе, а `is_active` или `role` невозможно установить
из тела запроса случайно.

## 8. Контейнера внедрения зависимостей нет

**Контекст.** Сервисам нужны часы, очередь, кеш, хранилище, шлюз.

**Решение.** Функции сборки в `container.py` и тонкий слой фабрик
в `api/deps.py`.

**Цена.** Список зависимостей нужно поддерживать вручную. Взамен путь
от обработчика до реализации читается глазами, а не выводится из
конфигурации контейнера.
