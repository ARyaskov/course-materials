# Архитектура nestor

## Почему log-structured

Точечное обновление файла на месте требует либо журнала, либо copy-on-write,
либо смирения с тем, что после сбоя питания файл окажется в состоянии,
которого не было ни до, ни после операции. Дозапись в конец файла с
контрольной суммой на каждую запись даёт другое свойство: любая запись
либо целиком легла на диск, либо не легла, и второй случай виден по CRC.

Плата — место: старые версии ключа остаются в файле, пока их не удалит
компакция. Выигрыш — последовательная запись (дружелюбна и к HDD, и к SSD)
и простое восстановление.

## Слои

```
        nestord (epoll, протокол)        nestor-cli    nestor-bench
                        \                    |            /
                         \                   |           /
                          ------------  libnestor  ------------
                                            |
        db.c        открытие, put/get/delete, восстановление, компакция
        index.c     hash-таблица ключ -> (файл, смещение, длина, seq)
        segment.c   файл сегмента: дозапись, чтение по смещению, скан
        record.c    кодирование записи, CRC
        hint.c      снимок индекса сегмента
                                            |
        util/       slice, buf, arena, pool, crc32c, hash, io, log, clock
```

Зависимости идут только сверху вниз. `util` не знает про хранилище,
хранилище не знает про сеть.

## Путь чтения

1. `nst_get` берёт read-блокировку.
2. Индекс отдаёт `nst_loc`: номер файла, смещение, длина, `seq`.
3. `pread` читает `rec_len` байт из нужного сегмента.
4. Декодер проверяет CRC и сверяет ключ с запрошенным.
5. Значение копируется в свежий буфер и отдаётся вызывающей стороне.

Одно обращение к диску на чтение — за счёт того, что весь индекс живёт
в памяти. Это же и главное ограничение: объём ключей ограничен ОЗУ.

## Путь записи

1. `nst_put` берёт мьютекс писателя (записи сериализуются).
2. При необходимости активный сегмент ротируется.
3. Запись кодируется в буфер и уходит `pwrite` в конец сегмента.
4. Под write-блокировкой обновляется индекс; счётчик живых байт старого
   сегмента уменьшается.
5. `fsync` по политике: `always`, `interval` или `never`.

## Компакция

Фоновый поток раз в `compaction_interval_ms` считает долю мусора среди
неактивных сегментов. Если она выше порога:

1. Резервируется номер для слитого сегмента, затем делается ротация —
   так слитый сегмент оказывается раньше нового активного и инвариант
   «активный сегмент последний» сохраняется после перезапуска.
2. Под read-блокировкой снимается список живых записей неактивных
   сегментов (ключ копируется в арену).
3. Байты записей переносятся в новый сегмент **без разбора**: CRC и `seq`
   сохраняются. Читатели и писатели в это время работают.
4. Под write-блокировкой индекс переключается на новые смещения — но
   только для тех ключей, чьё расположение не изменилось за время слияния.
5. Старые файлы удаляются, каталог синхронизируется.

Надгробия при слиянии исчезают вместе с данными, которые они скрывали:
сливаются сразу все неактивные сегменты, поэтому «воскресить» удалённый
ключ нечему. Сбой в середине компакции безопасен: старые сегменты ещё на
месте, а `seq` расставит версии правильно.

## Блокировки

| Что | Чем защищено |
| --- | --- |
| индекс, список сегментов | `pthread_rwlock_t lock` |
| дозапись в активный сегмент, `seq` | `pthread_mutex_t write_mu` |
| одновременность компакций | `pthread_mutex_t compact_mu` |
| длина сегмента | `_Atomic uint64_t size` |
| счётчики метрик | атомарные операции с `memory_order_relaxed` |

Порядок захвата всегда один: `compact_mu` -> `write_mu` -> `lock`.
Обратного порядка в коде нет, поэтому взаимной блокировки не возникает.

## Что сознательно не сделано

- Нет диапазонных запросов: hash-индекс их не поддерживает. Для них нужен
  LSM-дерево с отсортированными таблицами — другой проект.
- Нет репликации и транзакций на несколько ключей.
- Индекс целиком в памяти: примерно 60 байт плюс длина ключа на запись.
- Одна база — один процесс-писатель, это обеспечивает `LOCK`.
